# netlist/lvs/ — LVS with the digital block (DigitalSine) included

This is the flow **used for the chip-level LVS**: the netlist generated by xschem already
contains the content of the digital block (and of the standard cells), and the LVS runs with
the **official** IHP script, in both flat and deep modes. Nothing here depends on the
customized deck in the `lvs/` folder (which is only a blackbox reference).

## Results

- `DAC4133_digital_top` (digital wrapper): LVS **PASS in flat and deep**.
- `DAC4133` (top, analog + digital): LVS **PASS in flat and deep**.
- Expected warnings that can be ignored: KLayout version (binary 0.30.11 vs Python package
  0.30.12) and "Matching nets ... from an ambiguous group of nets" (symmetric nets, such as
  bus bits and differential pairs).
- In the log summary, `Status: PASS` **is not enough**: check `Errors: 0` and the line
  `Congratulations! Netlists match`. A KLayout failure before the comparison can also show
  up as PASS, with `exit code 1` and "no explicit PASS/FAIL signature found".

## Files

Essential (the chip-level LVS depends on them):

| File | What it is |
| --- | --- |
| `DigitalSine_com_stdcells.spice` | Standard cells cdl + digital block netlist. This is the file the symbol includes. |
| `DigitalSine_ordered.spice` | Digital block netlist (Magic) without black boxes, with the header in the xschem pin order. |
| `sg13g2_stdcell_lvs.cdl` | PDK standard cells cdl, without the `.end` line. |
| `../layout/DigitalSine.spice` | Digital block netlist extracted by Magic (origin of everything). |

Intermediate files and records (can be ignored): `DigitalSine_no_bb.spice`,
`DAC4133_digital_top_sem_stub.spice`, `DAC4133_digital_top_all*.spice`,
`DAC4133_digital_top_inc.spice`, `DAC4133_digital_top_lvs.spice`. The wrappers contain
**absolute paths of the development environment**.

## How to generate `DigitalSine_com_stdcells.spice`

Repeat these steps whenever the digital block changes. From the root of `DAC4133-main`:

```bash
# 1. standard cells cdl, without ".end"
sed '/^\.end[[:space:]]*$/Id' /opt/pdks/ihp-sg13g2/libs.ref/sg13g2_stdcell/cdl/sg13g2_stdcell.cdl \
  > netlist/lvs/sg13g2_stdcell_lvs.cdl

# 2. digital block netlist, without the standard cells black boxes and without ".end"
sed -e '/^\* Black-box entry/,/^\.ends/d' -e '/^\.end[[:space:]]*$/Id' \
  netlist/layout/DigitalSine.spice > netlist/lvs/DigitalSine_no_bb.spice

# 3. reorder the ".subckt DigitalSine" header to the pin order of the xschem symbol
python3 - <<'EOF'
import re
src = open("netlist/lvs/DigitalSine_no_bb.spice").read()
pins = ["VGND","VPWR","clk","rst","sign","signB"] + [f"sine_out[{i}]" for i in range(17,-1,-1)]
novo = ".subckt DigitalSine " + " ".join(pins)
src = re.sub(r"^\.subckt DigitalSine[^\n]*(\n\+[^\n]*)*", novo, src, count=1, flags=re.M|re.I)
open("netlist/lvs/DigitalSine_ordered.spice", "w").write(src)
EOF

# 4. join everything into a single file
{ cat netlist/lvs/sg13g2_stdcell_lvs.cdl; echo
  cat netlist/lvs/DigitalSine_ordered.spice; echo
} > netlist/lvs/DigitalSine_com_stdcells.spice
```

Why each step:

- **cdl instead of the standard cells spice:** in `sg13g2_stdcell.spice` the transistors are
  written as `XN0 ... sg13_lv_nmos` (subcircuit calls). The KLayout deck does not recognize
  them as devices, the standard cells end up empty and the whole schematic disappears. In the
  `cdl` they are `MN0 ...` (transistors).
- **No `.end`:** it ends the SPICE reading in the middle of the file.
- **No black boxes:** the Magic `.spice` starts with empty `.subckt` definitions of the
  standard cells; if they stayed, the cells would be defined twice.
- **Reordered header:** the symbol call in xschem is positional
  (`VGND VPWR clk rst sign signB sine_out[17] ... sine_out[0]`) and Magic lists the pins in
  alphabetical order. The body uses the pins by name, so reordering only the header does not
  change the circuit. If the symbol changes, update the `pins` list.

## How xschem uses it

In `schematic/xschem/DigitalSine.sym`, symbol properties (key `q`):

```
type=subcircuit
format="@name @pinlist @symname"
template="name=x1"
spice_sym_def=".include \"<path>/netlist/lvs/DigitalSine_com_stdcells.spice\""
```

- With `spice_sym_def`, xschem writes the `.include` in the netlist and **stops emitting the
  empty `.subckt DigitalSine`** from `DigitalSine.sch`.
- **Only one `.include` per `spice_sym_def`.** xschem reads everything after `.include` as a
  single path (which is why the standard cells are inside the same file).
- **The quotes are required.** The hyphen in `DAC4133-main` makes the KLayout SPICE reader
  cut the file path without them.
- When generating the netlist, the xschem LVS option ("top level is a .subckt") must be
  checked. Without it the top does not come out as a `.subckt`, and the LVS reports that it
  cannot find the schematic counterpart of the top cell. The option is not kept between
  sessions.
- xschem opens the `.include` file when generating the netlist. If the path does not exist,
  it shows `has_included_subcircuit: error opening file` and aborts.

## The `.include` path (attention)

The path in the symbol is currently an **absolute path of the development environment**:

```
/home/designer/shared/libs/IHP__DAC4133/DAC4133-main/netlist/lvs/DigitalSine_com_stdcells.spice
```

In the chip (repository `IHP__MPC2585`) this project is a submodule, and the chip schematic
references the symbols by absolute path in its own environment
(`/foss/designs/IHP__MPC2585/dependencies/IHP__DAC4133/DAC4133-main/schematic/xschem/...`).
For the chip xschem to generate the netlist, the `.include` in the symbol must point to:

```
/foss/designs/IHP__MPC2585/dependencies/IHP__DAC4133/DAC4133-main/netlist/lvs/DigitalSine_com_stdcells.spice
```

To be agreed with the chip maintainer:

- Who changes the path in the symbol (ideally a new commit in this repository).
- How the chip netlist is generated and delivered to IHP. An `.include` with an
  environment path does not exist there, so the final netlist may need to be self-contained.
- `DigitalSine_com_stdcells.spice` already includes the standard cells. If another project
  also includes them, the chip netlist may end up with duplicated `sg13g2_*` definitions.
- An alternative to test: `spice_sym_def="tcleval(.include \"[abs_sym_path DigitalSine_com_stdcells.spice]\")"`
  with the `.spice` in the same folder as the symbol. It has not been tested, and the chip
  schematic references the symbols by absolute path, so `abs_sym_path` may not find the file.

## How to run the LVS

With the IHP GUI in KLayout (it asks for the GDS top cell and the path of the `.spice`), or
with the official PDK `run_lvs.py`
(`/opt/pdks/ihp-sg13g2/libs.tech/klayout/tech/lvs/run_lvs.py`), always with the netlist
generated by xschem:

```
schematic/xschem/simulations/DAC4133_digital_top.spice     (top = DAC4133_digital_top)
schematic/xschem/simulations/DAC4133.spice                 (top = DAC4133)
```

Run in both flat and deep modes.

## Notes

- The digital `.spice` comes from the layout itself (Magic). The LVS checks the connectivity
  around `DigitalSine`, the hierarchy and the mapping of the standard cells, but **not the
  logic** of the digital block, which is verified in the digital flow LVS (OpenLane).
- In flat mode, pin labels of `DigitalSine` in the GDS create name conflicts with the labels
  of the wrapper. The labels were only needed in the blackbox flow (`lvs/` folder).
- In the `DAC4133` top, some sublevel pins exist in the layout, with no counterpart in the toplevel
  schematic (`ISUM`, `en_bb`, `xa`, `xb`). The deck accepts them, but it is worth checking
  with IHP whether internal labels inside macros are allowed.
  LVS flat passes with and without these pins. LVS deep fails without them.
- Pin labels must be on the text layer (`.text`) for the deck to read them.
